### User · 05:47

docker builds a new image with each redeploy. do they stack up or are old ones deleted?

### Claude · 05:47

They pile up. Old images are not deleted automatically.

**Why:** `docker-compose.yml` has `build: .` and no `image:` name, so Compose tags the image `<project>-app:latest`, e.g. `mercator-app:latest`. On each `docker compose build`:

- **The tag moves to the new image.** The previous image loses its tag and becomes a "dangling" image (`<none>:<none>`). It stays on disk, typically a few hundred MB each with the Typst fonts and the release.
- **The build cache grows too,** with old layers from earlier builds.

The database and the uploads live in volumes, so cleaning up images doesn't touch them.

**Cleanup:**

```sh
docker image prune -f                          # removes untagged images only; the running one is tagged
docker builder prune -f --filter until=168h    # build cache older than a week; recent layers keep builds fast
docker system df                               # shows how much space images, cache and volumes use
```

`docker image prune` is safe to run right after `docker compose up -d`, because the running container uses the newly tagged image. Avoid `docker system prune -a --volumes`, which would delete the volumes and with them the database and uploads.

Neither `DOCKER.md` nor the operating guide mentions this yet. Should I add `docker image prune -f` to the update steps and a short cleanup section to the maintenance chapter (de, en)?
