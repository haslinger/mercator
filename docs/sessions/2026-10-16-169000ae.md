### Claude · 13:28

Because `change_password` is the stock action from the ash_authentication generator, and it requires the old password as a re-authentication step ([user.ex:97-118](lib/mercator/accounts/user.ex#L97-L118)). The idea is that an active session alone shouldn't be enough to change the password. If someone gets your session (an unlocked computer, a stolen cookie), they can't lock you out permanently by setting a new password.

Your case shows the weak spot in that idea. Logging in with a magic link already proves you control the email address, and that is all a password reset checks. So asking for the old password afterwards adds no security. It just gets in your way.

**How to do it today:** the sign-in page has a "forgot password" link (route `/reset`, [router.ex:177](lib/mercator_web/router.ex#L177)). It sends a reset email, and the reset form (`reset_password_with_token`) only asks for the new password twice.

**A real gap:** `hashed_password` can be empty, so users who only ever signed in by magic link have no password at all. The account page can never work for them, because there is no "current password" to type.

**Suggestion (#N, for you to decide):** let the account page set a password without the old one in two cases:
1. the user has no password yet, or
2. the user signed in by magic link within the last few minutes.

Otherwise it would keep asking for the current password. Ash can check this through a custom validation that looks at the user's `hashed_password` and the sign-in method or time stored in the token. Or, more simply, the account page could add a "Send me a reset link" button next to the form.

Should I build one of these? The reset-link button is small. The "recent magic link" version is nicer to use but needs the sign-in time stored on the session or token.
