**The three options**

| | Effort | Fits when |
|---|---|---|
| **Copy** | Hours. Copy the files, rename the modules, drop the shop blocks, run `mix ash.codegen`. | The other project uses the same stack (Phoenix, Ash, DaisyUI, Postgres) and you're fine with the two copies drifting apart. |
| **Umbrella app** | Medium. | Hardly ever here. An umbrella splits *one* product into apps in *one* repo. To share the CMS, the other project would have to live in Mercator's umbrella. |
| **Library** (Hex, or just a git/path dependency) | 1–2 weeks to do properly. | Two or more projects keep using it and you want fixes to reach both. |

**What makes the library route expensive (Ash-specific)**

1. **Resources inside a library:** they need the host app's repo, its user resource for versions and its role check. That means configuration set at compile time, or generating the resources in the host app the way `ash_authentication` does. This is the biggest piece of work.
2. **Migrations:** the host has to generate them for the library's resources, and every CMS update then means new codegen in every host.
3. **Blocks have to become pluggable:** you'd need a block behaviour plus a registry, so that Products, Categories and Contact options live in Mercator and the other project can register its own.
4. **The admin LiveViews** would need a host layout, an auth hook and a Gettext backend handed in, plus a router macro like `cms_routes "/admin/pages"`.

**Recommendation**

1. **Copy now.**
2. **Optionally, tidy the seams in Mercator first (about a day).** Move the Catalog and Consulting blocks behind a small block behaviour, and route `Translated`, `Uploads` and `ActorHasRole` through one config point. The copy gets cleaner, and the later extraction becomes mostly mechanical.
3. **Extract a library** once the second copy needs a fix the first one already got.

Having looked at qed, I'm more sure copying is right. qed shares the stack, but it uses a different database and does a different job, so a shared library would have to bridge two quite different setups.

**Where qed and Mercator differ**

| | Mercator | qed |
|---|---|---|
| Database | Postgres (AshPostgres) | **SQLite** (AshSqlite) |
| Output | Pages rendered live by LiveView | **Static HTML** sites, uploaded by ZIP, SSH or GitHub Pages |
| Scope | One site per deployment | **Many podcasts per instance**, each with members (owner/editor) |
| Languages | de/en content in JSONB | English only so far |
| Background jobs | Oban | None yet (qed backlog #013) |

**What would have to change in the CMS for qed**

- **Postgres-only code:** raw SQL in [set_page_path.ex](lib/mercator/content/changes/set_page_path.ex) (uses `gen_random_uuid()`, `ANY($3)`, `ON CONFLICT`), [asset_unused.ex](lib/mercator/content/validations/asset_unused.ex) (`blocks::text`), the asset search (`->>`, `ILIKE`, `array_to_string`) and the tag list (`unnest`). The block arrays and the `tags` array also have to be stored differently in SQLite.
- **One site per podcast:** pages, paths and assets need a `podcast_id`, paths are unique per podcast, and policies switch from Mercator's roles to qed's `PodcastRole`.
- **Static output:** blocks are rendered to HTML files instead of LiveView pages. Redirects become redirect files. The contact form, the submissions and the Contact options block don't fit a static site.
- **Things to drop:** the Products and Categories blocks, the Consulting links and probably the de/en translations.

A shared library would have to support both databases, both one-site and many-sites, and both live and static rendering. That's the expensive kind of library, and only two projects would use it.

**Recommendation**

1. Copy the pieces qed needs into a `Qed.Content` domain and adapt them there.
2. The Markdown editor (qed backlog #022) is small and stands alone, so copy it first.
3. Look at a library again only if a third project shows up that is close to Mercator, for example one on Postgres.
