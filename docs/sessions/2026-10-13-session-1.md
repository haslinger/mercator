- Editors maintain this content, and it must be searchable, exactly as in Rails.
- So #7 is only about how the database stores it:

| | (a) Separate columns (`title_de`, `title_en`) as in Rails | (b) One JSONB column per attribute (`title: %{"de" => …, "en" => …}`) |
|---|---|---|
| Searching | Simple; one full-text index per column | Equally possible: one full-text index per language on `title->>'de'` with the German stemmer, on `->>'en'` with the English one |
| Sorting / filtering | Trivial | Works through expressions (`title->>'de'`), slightly more verbose |
| Adding a language | Migration on every translated table | No migration, only config |
| Ash code | Two attributes, plus a calculation for "current language with fallback" | One attribute, plus the same kind of calculation (`de` as fallback) |
| Forms | Two fields | One component that renders one input per language |

Searching works with both. In PostgreSQL you'd use full-text search with a separate index per language. That works better than MySQL's `LIKE` and gives proper word stemming: a German search for "Drucker" also finds "Druckern".

**My recommendation: (b) JSONB.** It keeps resources lean, adding a language is just configuration, and searching per language works fully with an index per language. The only real cost is slightly more verbose sorting in SQL, which we'd hide behind a calculation once anyway.

### Claude · 10:54

I'd drop the database row per visitor. The counting need is real, but a users table is the wrong place for it.

**Why the Rails approach was costly:**
- The users table fills up with "Gast" rows, which needed an hourly cleanup cron.
- Every visit costs a database write, and every bot creates a "user".
- Statistics, permissions and the user list all have to filter out guests.
- It doesn't even count well: no cookie means a new "user", and the cleanup deletes the history.

**Visitor counting, in two layers:**

1. **General traffic** (visitors, page views, referrers): outside the app.
   - Either via proxy logs (e.g. GoAccess on the nginx logs), or with a privacy-friendly tool like Plausible, Umami or Matomo.
   - Proxy logs are cheap but crude, because bots and asset requests distort them.
   - With single tenant, each customer can choose their own tool, so the app shouldn't hard-wire one.
2. **Shop funnel** (anonymous visitors → basket → checkout → order): inside the app.
   - The proxy can't see this; only the app knows when a basket is created or an order placed.
   - It could be a small, anonymous event table (session ID, event, timestamp; no personal data), written asynchronously. That's essentially what Ahoy's `Visit` and `Event` were in Rails, minus the fake users.
   - It also matters for GDPR: counting anonymously without storing IP addresses avoids most consent problems.

**My opinion:**
- Decide #8 now as recommended: an anonymous session basket that moves to the real user at login or registration.
- Treat analytics separately, under the existing question **#18**. The funnel events are worth having, but they aren't needed for phase 1. I'll design the session basket so it carries an anonymous session ID that we can attach events to later.
