**Rate limiting inside the app (your question on #83):** the usual tool is the **Hammer** library. It keeps a counter per key and time window in the app's memory, e.g. "contact form from IP 1.2.3.4: 3 in the last hour". When the limit is reached, the form is rejected with a friendly message, before anything is stored or emailed.
- **Behind your proxy:** the app sees the proxy's IP, not the visitor's. Plug's built-in `Plug.RewriteOn` takes the real client IP from the `X-Forwarded-For` header. It must only trust that header when the request comes from your proxy, so no extra library is needed for this part.
- **Several servers:** the in-memory counter is per server. With more than one app instance you'd switch Hammer to Redis, but one instance per customer is the plan.
- **Why in the app as well as at the proxy:** the app can limit per *action* (contact form, sign-in, password reset) and per email address, which a proxy can't tell apart.

**How content is checked against the extension:** the code is in [file_types.ex](lib/mercator/content/file_types.ex).

1. **The extension must be on the list.** Anything else, such as `.exe`, `.html` or `.svg`, is rejected before its content is looked at.
2. **The first bytes must match that extension's format.** Most file formats start with a fixed signature, sometimes called "magic bytes":

| Extension | Format | Expected start |
|---|---|---|
| .doc, .xls | old Office container (OLE) | `D0 CF 11 E0 A1 B1 1A E1` |
| .docx, .xlsx, .odt, .ods | ZIP archive | `PK 03 04` |
| .dwg | AutoCAD drawing | `AC10` (then the version, e.g. `AC1032`) |
| .dxf | AutoCAD exchange format (text) | valid text starting with `0` / `SECTION` |

A web page or script renamed to `Angebot.docx` doesn't start with `PK 03 04` and is rejected. A test covers exactly that case.

**Limits of this check:** it confirms the file is plausibly what it claims, not that it's a valid document. Any ZIP renamed to `.docx` would pass. That's acceptable because of how these files are handled afterwards:
- They're always served as downloads (`Content-Disposition: attachment`), never opened in the browser.
- The `nosniff` header stops the browser from guessing the file type itself.
- The server never opens or runs them.

**Possible stricter check:** for the ZIP-based formats I could look inside the archive. Word and Excel files contain a `[Content_Types].xml`, and LibreOffice files contain a `mimetype` entry naming the exact type. Erlang's built-in `:zip` module can do this cheaply, so nothing new would need to be installed. Shall I add it?
