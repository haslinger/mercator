### Claude · 07:43

Yes, that's expected, and it isn't specific to Android or the PWA. Every device loses its login at 3 o'clock in the demo deployment.

Here's why:

- `Mercator.Demo.reset/0` ([demo.ex:136](lib/mercator/demo.ex#L136)) runs `TRUNCATE … RESTART IDENTITY CASCADE` on every table except the migrations and Oban tables. That wipes `users` and the token table too.
- The token config in [user.ex:29-34](lib/mercator/accounts/user.ex#L29-L34) sets `store_all_tokens? true` and `require_token_presence_for_authentication? true`. A remember-me JWT is only accepted if its row still exists in the token table. After the truncate the row is gone, so the cookie is rejected even though its signature is still valid.
- The seeds also create the demo users again from scratch. Unless they get the same IDs as before, the token's subject (`user?id=…`) points to a user that no longer exists.

So the 30-day cookie only lasts until the next reset. In a real customer deployment there's no nightly reset, and remember-me works as intended.

If you'd like logins to survive the reset in the demo (say, so sales staff can try out the PWA over several days), there are two options:
1. Seed the demo users with fixed UUIDs, and leave the `tokens` table (and `users`) out of the truncate. This gets complicated because of the cascades.
2. Accept it and add "including logins" to the reset hint in [demo_components.ex:56](lib/mercator_web/components/demo_components.ex#L56).

I'd go with option 2, since the demo is meant to be ephemeral. Should I make that change?
