My recommendation is neither seeding nor copying: the documentation is **compiled into the app from the files where they already live**.

**Integration**

A module `Mercator.Docs` reads the Markdown files when the app is compiled and turns them into a fixed set of chapters:
- **What each chapter knows:** a short header in each file gives title, audience (roles), order, and which admin page its "?" belongs to. The module renders the text with the existing `MercatorWeb.Markdown` and builds the table of contents and the search index.
- **No copies:**
  - manuals and shop help: `priv/docs/<locale>/…`;
  - developer chapters: the existing `docs/*-design.md` files, read in place;
  - making-of: `docs/sessions/*.md` and `docs/metrics.md`, also read in place.
- **Recompile on change:** every source file is registered with the compiler, so editing it recompiles the module, in dev too.

Why this approach:
- **Same version as the code:** every release carries exactly the documentation of its own code. There's no database content that can drift and nothing to migrate.
- **Errors show up early:** a missing title or a broken "?" link fails the build or a test, instead of turning up at runtime.
- **Docker image:** the image only ships `priv/`, so the `docs/` folder isn't in it. Because the content is compiled in, that doesn't matter; the build stage only needs `docs/` copied in.

The alternatives, and why I'd skip them:
- **Seeding into the CMS:** this creates a second copy that people can edit and that drifts from the code version. The CMS stays for customer content (#125).
- **Reading the files at runtime:** this works too, but `docs/` would then have to be copied into the release, and errors would only show up when someone opens a page.
