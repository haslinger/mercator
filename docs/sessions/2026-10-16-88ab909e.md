**How it works:** almost as you describe it, but you can close more than the browser. Once the phone is set up, you don't need the browser open at all.

**One-time setup, per phone:**
1. Open the shop in Chrome on the phone and sign in.
2. Tap a button such as "Notify me on this phone" on the desk or the account page.
3. Android asks "Allow notifications?" When you say yes, Chrome creates a **push subscription**. This is an address at Google's push service, plus keys that only this phone can decrypt with.
4. The shop saves that address on your user account.

**When a customer writes:**
1. The shop encrypts a short message ("New conversation: Karl Luchs") and sends it to that address with an HTTP POST.
2. Android phones keep one permanent connection to Google's servers for all apps (it's the same mechanism WhatsApp or Gmail use). The message arrives over that connection.
3. Android wakes Chrome in the background. Chrome runs the shop's **service worker** (`sw.js`), a small script registered with the browser rather than with a tab. The service worker shows the notification.
4. When you tap the notification, the conversation opens on the desk.

**What this means in practice:**
- You can close the tab and swipe Chrome away from the recent apps, and notifications still arrive. The service worker doesn't need an open page; Chrome starts it just for the message.
- **The login doesn't have to stay alive.** The subscription belongs to the phone and is stored with your user, so it doesn't depend on the session. Notifications keep coming even after the session runs out; you'd only have to sign in again when you tap one. Signing out (or a switch on the account page) should delete the subscription, so a shared phone stops getting them.
- **Things that stop it:**
  - blocking notifications for the site
  - "Force stop" on Chrome in the Android settings, until Chrome is opened again
  - aggressive battery savers on some brands (Samsung, Xiaomi, Huawei), which can delay or swallow messages; there you exempt Chrome from battery optimisation
- Android's sleep mode can delay normal messages. We'll send ours as urgent so they come through right away.
- **Optional:** "Add to home screen" installs the shop as an app with its own icon. Android doesn't need this, but iPhones do: they only get push for shops added to the home screen.

So your sales people set it up once per phone, and from then on their phone buzzes whenever a customer starts a conversation or writes to them.

### Claude · 18:16

No. Web Push costs nothing and needs no account at Google.

- **No Google account, Firebase project or API key.** We create the key pair (VAPID) ourselves, once per deployment, and keep it in the runtime config. The key tells the push service which server is allowed to send to a subscription.
- **The browser picks the push service, not us.** Chrome uses Google's, Firefox uses Mozilla's, and Safari uses Apple's. The shop just POSTs to whatever address the phone gave it. All three are free, because browser makers run them as part of the web platform.
- **The limits don't matter for us.** A message can be up to about 4 KB, and there are rate limits meant for mass senders. A handful of consultants getting a few notifications a day is far below those.
- **Google can't read the messages.** They are encrypted with the phone's keys. Google only sees that some server sent something to some subscription.

Even a native Android app would use Firebase Cloud Messaging, which is also free. With Web Push we don't need that either.

I see, and is there the risk of big delays, like with SMS, where you don't have any guarantees for delivery times?

### Claude · 18:17

There's no guarantee, as with SMS. In practice, though, it is usually much faster and more predictable than SMS.

**Normally it takes about one to two seconds.** The phone's connection to Google is always open, so nothing is queued at a carrier the way SMS is.

**Where delays can come from:**
- **Android's sleep mode (Doze).** When the phone lies still with the screen off, Android holds back normal messages until its next wake-up window, which can take minutes. Messages marked as **urgent** are delivered at once. We'll send ours as urgent. Android only downgrades apps that send urgent messages without showing a notification, and we always show one.
- **Manufacturer battery savers** (Samsung, Xiaomi, Huawei). This is the most common real-world cause of late or missing notifications. Exempting Chrome from battery optimisation fixes it. I'd put that in a short setup note for staff.
- **The phone is offline.** The push service keeps the message for as long as we allow (the TTL) and delivers it when the phone is back. I'd keep that short, about 15 minutes. A "customer is waiting" message from hours ago is useless, and it's better if it never arrives.

**What we can't know:** the push service confirms that it **accepted** the message, but not that the phone showed it. There is no read receipt, unless we build one ourselves (the service worker could report back when it shows a notification).

**So I'd treat the phone notification as an extra signal, not the only one:**
- The desk keeps ringing as it does now.
- If nobody accepts a new conversation within a few minutes, the customer gets a fallback, such as "Leave your number or email, we'll get back to you." This would mostly matter later, when the shop runs without staff watching the desk.

For the prototype, urgent messages, a short TTL and a setup note about battery optimisation are enough. Should I record the fallback idea as a backlog question (#154)?
